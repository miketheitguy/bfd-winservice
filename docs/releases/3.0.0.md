# BFD Windows Service v3.0.0

Cowabunga, release crew. This release restores meticulous keyed MD5,
reuses unchanged classical keyed-SHA1 transmissions, and lets BFD and its BGP
broker start independently.

## Compatibility and version selection

The published baseline is v2.0.2. Adding `AuthType::MeticulousMd5` to the
public, exhaustive Rust `AuthType` enum breaks downstream matches that cover
only the four previous variants. The repository's public contract includes
Rust APIs, so the complete change set requires **v3.0.0**, following the
[version policy](../../CONTRIBUTING.md#choose-a-release-version) and
[Cargo's enum compatibility guidance](https://doc.rust-lang.org/cargo/reference/semver.html#enum-variant-new).
Rust consumers must handle the restored variant and rebuild.

Service lifecycle behavior also changes: BFD no longer requires a Running
broker at startup, verifies no broker connection during startup, and performs
no idle broker probe or restart-triggered replay of a completed BGP action.
Outstanding failed actions still retry. Deployments that relied on automatic
reconciliation after a broker-only restart must account for its removal;
future BFD transitions still queue their corresponding actions. See
[BGP worker behavior](../reference/bgp-provider.md#worker-retries-and-broker-recovery).

Upgrade both services together with `BfdWinService-3.0.0-x64-setup.exe`.
The private BGP control interface is version 2; don't mix old and new service
binaries. Existing registry configuration, authentication selections, and logs
are retained. No registry migration is required. Distribution remains the
offline setup executable and its SHA-256 checksum, with the same Windows and
x64 Visual C++ runtime requirements.

## Added

- Restore `Auth=meticulous-md5`, wire type 3, for classical BFD and S-BFD.
  Classical multihop BGP control accepts either meticulous MD5 or meticulous
  SHA1. Non-meticulous MD5 remains unsupported. Choose matching peer settings
  using the [authentication configuration](../configuration.md#authentication)
  and [performance and compatibility guidance](../security/authentication-performance.md).

## Changed

- Classical `keyed-sha1` sessions reuse the last successfully transmitted
  packet and digest while its contents match and its age is less than one
  second. Local state changes invalidate reuse, even if state returns before
  the next send. Content changes or expiry advance the sequence once; failed
  sends don't commit a new sequence. Receive verification remains per packet.
  Both meticulous modes and S-BFD probe correlation retain their sequence rules.
- Remove BFD's SCM dependency on the broker. Install, upgrade, and repair clear
  the obsolete dependency; failed-upgrade rollback restores the original list.
  The broker retains its Windows `RpcSs` dependency.
- Remove dedicated BGP connection probes, startup status checks, and broker
  instance tracking. Functional Get/Start/Stop calls still authenticate both
  service identities. Both local RPC channels require the expected service SID
  in any nonempty caller restricting list, alongside the exact account and
  enabled service group checks.
- Consolidate operator, developer, and security documentation around canonical
  references. Retain both diagram image sets and align the Mermaid and Draw.io
  explanations.
- Run the full GitHub validation workflow on pull requests targeting `main`
  and release-tag pushes. Ordinary branch pushes, including `main`, don't run it.

## Validation

Release publication requires optimized tests, Rust/native AddressSanitizer
tests, bounded fuzz campaigns, production executable hardening, and native
MSI/bundle installation, rollback, repair, and removal checks. The upgrade
fixture uses the published v2.0.0 bundle and verifies restored executable bytes,
typed configuration, service policy, generated logs, and mutual RPC
authentication. It doesn't certify every historical upgrade or external peer.

Regression coverage includes keyed-SHA1 digest reuse and expiry, every local
state transition, wraparound, failed-send retries, and S-BFD reply consumption.
The classical fuzz oracle also checks authenticated transmission and relative
sequence progression against a session that skips rejected inputs. Meticulous
MD5 has digest vectors, replay-window, and native loopback coverage; no
external-peer MD5 interoperability or comparative deployment CPU benchmark is
claimed. See the [validation guide](../development/validation.md) and
[dated review receipts](../../CODE_REVIEW.md) for scope and limits.
