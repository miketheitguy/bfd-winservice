# BFD Windows Service v3.0.2

Cowabunga, service crew. Both Windows services now start with only
`SeChangeNotifyPrivilege` in their SCM privilege allowlists. BFD no longer
retains `SeCreateGlobalPrivilege`, and the broker's minimum applies when SCM
creates its process, before loader initialization.

## Compatibility and version selection

The published baseline is v3.0.1. These are compatible least-privilege and
installer rollback fixes, so **v3.0.2** follows the
[version policy](../../CONTRIBUTING.md#choose-a-release-version).
Public Rust APIs, command-line options, registry settings, BFD interoperability,
private RPC interfaces, supported Windows versions, and runtime requirements
remain compatible. No configuration migration is required.

Upgrade both services together with `BfdWinService-3.0.2-x64-setup.exe`.
Installation and repair apply the reviewed privilege lists; the services remain
stopped until you start them. BFD retains its restricted LocalService identity,
and the broker retains its LocalSystem identity and existing MI policy.
Distribution remains the offline setup executable and its SHA-256 checksum.

## Security and installer fixes

- Remove `SeCreateGlobalPrivilege` from BFD's runtime and SCM allowlists.
  BFD permanently retains only `SeChangeNotifyPrivilege` before accepting work.
- Apply the broker's existing runtime minimum through SCM as well. Both services
  retain startup privilege reduction as an additional enforcement layer.
- Snapshot both services' exact prior privilege policies before installer
  mutation. Rollback restores absent, explicitly empty, and ordered explicit
  lists, including after a partial privilege commit. Snapshot parsing bounds
  native data and rejects malformed or oversized storage.
- Validate both SCM lists and actual service tokens after installation and
  repair. Successful upgrades apply both minimum lists; failed upgrades preserve
  the previous policies, executable bytes, configuration, and logs.

See [service isolation](../security/service-isolation.md) for the identities,
privilege limits, and rollback behavior. The broker's SYSTEM account still
confers administrative authority through its account and group memberships.

## Validation

Before release version stamping, the complete functional change set passed on
Windows Server 2025 against Ubuntu 26.04.1 with BIRD 2.18:

- All 46 VM scenarios: 24 authentication cases, three isolated BIRD-controlled
  and three Windows-controlled withdrawal/recovery cycles, two BGP-only cases,
  and 14 service, peer, packet, process, and adapter interruption cases.
- Logging-disabled client failure reporting and recovery, followed by a
  two-minute BFD/BGP and route stability observation.
- 289 native VM checks, including real RRAS queries, RPC/MI coexistence,
  executable hardening, and the installer snapshot regressions.
- Nine actual privilege-mutation rollback cases covering either or both
  services with absent, empty, and explicit prior lists.
- Fresh install, repair, removal, forced MSI rollback, runtime prerequisite
  installation, bundle maintenance, and published v2.0.0 upgrade/rollback.
- A major-upgrade commit failure after the first successful privilege write:
  rollback restored both exact prior policies and both published executable
  hashes. The candidate was restored and final stability/token checks repeated.

Final checks verified both SCM lists and running tokens, BFD's restricted SID,
original configuration and keys, executable ACLs, BIRD configuration, and fault
cleanup. Other supported Windows versions were not exercised by this VM run.

Publication requires the release-tag workflow's optimized tests, Rust/native
AddressSanitizer, fuzz campaigns, production hardening, and installer/upgrade
checks to pass for the versioned source. See the
[validation guide](../development/validation.md) for scope and limits.
