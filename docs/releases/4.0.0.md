# BFD Windows Service v4.0.0

Cowabunga, service crew. BFD runs only as an installed Windows service. Both
daemons verify their SCM-issued minimum privileges without modifying their
tokens. Foreground execution, public help/version options, and STDOUT logging
are removed.

## Compatibility and version selection

The published baseline is v3.0.2. Removing the supported CLI and public Rust
APIs breaks the documented contract, so the complete change set requires
**v4.0.0** under the
[version policy](../../CONTRIBUTING.md#choose-a-release-version).
Foreground wrappers, scheduled tasks, output collectors, and library callers
must migrate. Existing installed-service deployments retain their registry
settings, accounts, SID types, BFD wire behavior, and private RPC interfaces.
No registry-schema migration is required.

Upgrade both services together with `BfdWinService-4.0.0-x64-setup.exe`.
Distribution remains the offline setup executable and its SHA-256 checksum,
with the same supported Windows versions and x64 native runtime requirements.
Installation and repair leave the services stopped for configuration and
verification.

## Breaking changes and migration

- BFD rejects every command-line argument, including `--console`, `--help`,
  `--version`, `-h`, and `-V`. Direct execution without arguments fails to connect
  to SCM. Stop older foreground processes and wrappers, install the setup bundle,
  and use `Start-Service` and `Stop-Service`. Follow the
  [foreground migration guide](../console.md).
- The broker also rejects public help/version options. Its four fixed private
  MSI transaction commands remain available to the installer.
- Read both executable versions from Windows file properties or PowerShell
  `VersionInfo`. Version validation no longer launches either daemon.
- Collect Operational ETW events or enable the optional file log instead of
  redirecting STDOUT. The foreground runner, Ctrl+C handler, and console logging
  branches are removed. Existing ETW payload layouts and numeric service Mode
  `0` are preserved. See [Logs and events](../logging.md).
- Rust callers must remove `config::CommandLine`, `Options::console`, and
  `runtime::drop_privileges` usage. Use `config::load_registry()`, `Logger::new()`,
  and `Logger::open(&options)` without a mode parameter. Library engine callers
  can still use `Engine::run_until` with `StopSignal`. See
  [library migration](../console.md#migrate-library-callers).

## Security

- SCM supplies only `SeChangeNotifyPrivilege` to both service processes. After
  identity checks, each daemon queries its existing token with `TOKEN_QUERY`
  and requires that exact privilege set with the required privilege enabled.
  A missing, disabled, or additional privilege, even a disabled extra, fails
  startup before configuration, sockets, RPC, or COM/MI initialization.
- Production startup no longer requests `TOKEN_ADJUST_PRIVILEGES` or repairs an
  overprivileged token. Repair the SCM policy and restart the service. Token
  adjustment remains confined to isolated test fixtures.
- BFD remains LocalService with a restricted service SID; the broker remains
  LocalSystem with its unrestricted service SID and existing COM/MI policy.
  The broker's account and groups still confer administrative authority.
  See [service isolation and policy diagnosis](../security/service-isolation.md).

## Validation

Before release version stamping, the service-only change set passed the
complete Windows Server 2025 / Ubuntu 26.04.1 with BIRD 2.18 VM scenario suite:

- 46 functional scenarios: 24 authentication cases, three isolated BIRD-controlled
  and three Windows-controlled withdrawal/recovery cycles, two BGP-only cases,
  and 14 service, peer, process, adapter, and packet interruption cases.
- 299 native VM checks, including 12 installed daemon argument/direct-launch
  rejection cases, real RRAS queries, RPC/MI coexistence, and executable hardening.
- Startup rejection after broadening either service's SCM privilege list,
  followed by recovery after restoring the minimum; actual running-token checks.
- Nine partial/full privilege rollback cases, plus fresh installation, repair,
  removal, forced MSI rollback, prerequisite installation, bundle maintenance,
  and published v2.0.0 upgrade/rollback.
- Two logging-disabled recovery phases and a final two-minute BFD/BGP and
  route stability observation.

Required Rust checks, optimized tests, Rust/native AddressSanitizer, fuzz
regressions, production packaging, and documentation checks also passed before
version stamping. See the [dated validation record](../service-only-validation-2026-10-22.md)
for local receipt locations, overlapping counts, harness corrections, and limits.
This VM run does not establish other Windows versions or every historical upgrade.

After stamping v4.0.0, the complete optimized native test suite, strict Clippy,
formatting, strict API documentation, release-version fixtures, and Markdown
and PowerShell checks passed again. The versioned offline bundle and private
MSI passed package validation, and both production executables passed the
release hardening harness.

Publication requires the release-tag workflow's optimized tests, Rust/native
AddressSanitizer, bounded fuzz campaigns, production hardening, and
installer/bundle/upgrade validation to pass for the versioned source. See
[development validation](../development/validation.md) for the test boundaries.
